# 流程

# 应用启动流程

冷启动，launcher从点击图标开始，通过代理方式，静态方法拿到ams的代理类，调用其中方法，来到system-server进程（ams所在），这时ams里有一个方法startSpecificActivityLocked会判断app进程是否存在（对应冷启动和热启动）；如果是冷启动，会向zygote进程发出请求，这时候会fork出应用app进程，调用ActivityThread.main()接口创建应用进程，主线程创建后会looper消息循环，并且通过IBinder和ams进行绑定，ams会将activityRecord传递给到应用进程；接着调用oncreate()、onstart()方法来到生命周期;接着ams通知wms添加窗口，然后调用activity的view层级触发draw方法，配合sf、choregrapher进行显示绘图。

ProcessRecord 在frameworks/base/services/core/java/com/android/server/am/ActivityStackSupervisor.java 中的startSpecificActivityLocked中被声明

也是这个方法里，ams通知启动 mService.startProcessLocked(r.processName, r.info.applicationInfo, true, 0, "activity", r.intent.getComponent(), false, false, true);

# input流程

首先是从硬件驱动层上报，这里遇到问题，一般查看日志tp报点，如果有异常会给到低软分析；接着来到system-server进程下的inputreader，该线程收集底层报点，将事件封装成input_event，包含时间戳，类型，数据等，接着来到InputManagerService，也就是IMS，预处理之后，通过InputDispatcher线程进行事件下发，这里逻辑就是事件会分发给当前的活动窗口，应用app接受事件，在trace上体现是搜索input能得到显示

# 开关机

从boot rom开始，到boot loader文件启动kernel，这个阶段对应bootprof就是preloader阶段，这块有耗时责任归到低软，接着从kernel启动后，到第一个用户进程init启动，加载rc文件，文件挂载阶段，接着创建java的父进程，zygote，会初始化好dalvik VM虚拟机，去创建出system-server进程，接着去启动ams，调用ams启动launcher，来到开机界面

# 显示流程

当界面的UI更变的时候，就会调用invalidate()标记脏区；这时会触发ViewRootImpl 的 scheduleTraversals() 方法； ViewRootImpl 在Choreographer 注册了回调，这时，在Choreographer会向底层请求下一次信号，Choreographer 通过 FrameDisplayEventReceiver 监听 VSYNC 信号；当 ​VSYNC 信号到达​ 时，Choreographer 会按以下顺序处理回调； ​INPUT（输入事件回调）​：处理触摸事件、动画等输入相关任务。 ​ANIMATION（动画回调）​：执行属性动画、过渡动画等。 ​TRAVERSAL（视图遍历回调）​：触发 View 系统的 measure、layout、draw。 ​COMMIT（提交回调）​：处理渲染完成后的提交任务

当执行到 ​TRAVERSAL 回调​ 时，ViewRootImpl 的 mTraversalRunnable 被调用。这会触发 ViewRootImpl.performTraversals()

# lmkd kswapd

lmkd是nactive进程，是android的功能；kswapd是内核自带的线程

kswapd： 内核进程，负责虚拟内存管理，通过页面置换（Page Out）将不常用的内存页换到磁盘。 触发条件：当物理内存不足且存在可交换空间时自动激活。 LMKD： 用户进程，属于 Android 系统服务，直接杀死进程以释放内存块（非页面级）

重度压力：若 kswapd 处理后仍不足，LMKD 触发进程杀死。

平衡： 过度依赖 kswapd：频繁换页会导致 IO 瓶颈，降低系统响应速度；以及占用cpu资源。 过度依赖 LMKD：频繁杀死进程可能引发应用崩溃或 ANR。

min low high， 低于min触发直接回收，

# wms

  1. 窗口管理层级 窗口添加/删除： 应用进程通过 WindowManager.addView() 请求添加窗口（如 Activity 窗口、Toast、系统提示窗）。 WMS 根据窗口类型（如 TYPE_APPLICATION、TYPE_STATUS_BAR）分配层级和权限。
  2. 布局与渲染 窗口布局计算： 根据屏幕尺寸、窗口参数（如 gravity、margin）确定窗口的位置和大小。 处理多窗口模式（如分屏、悬浮窗）的布局冲突。 渲染协调： 与 SurfaceFlinger 合作，将窗口内容合成到屏幕缓冲区（BufferQueue）。 管理窗口的可见性（VISIBLE/INVISIBLE）和焦点切换。
  3. 事件分发 输入事件处理： 通过 InputManager 接收触控、键盘等输入事件，根据窗口的焦点状态分发给对应的 Activity。 支持手势识别（如滑动、缩放）的传递。
  4. 系统界面控制 状态栏/导航栏管理： 控制状态栏（StatusBar）和导航栏（NavigationBar）的显示与隐藏。 动态更新系统UI元素（如电池电量、信号强度）。 锁屏/亮屏联动： 监听屏幕状态变化（onScreenOff()/onScreenOn()），通知应用进程调整界面。

# app性能

  • crash解决 java crash navtive crash
  1. 确立app的crash的基本信息，从events-log搜索am_crash以及mobile-log中打印的crash_log日志
  2. 确认该apk发生crash时的周围情况，从logcat中找到当时的cpu、内存、io的占用信息
  3. 进一步搜集内存和cpu的详细信息，proc/meminfo 、dumpsys_meminfo 等

crash大概分为三类， java层、native层、anr；一般java层都比较简单可以通过日志查看堆栈找到对应代码，很容易看到crash的原因、比如空指针，oon内存不足等；native比较复杂，需要查看signal（信号）、code、fault addr（错误地址） 等内容，以及崩溃时 Java 的堆栈； 确立crash后，一般可以try catch捕获一下

# Android ANR 深度案例分析：SystemServer 崩溃实战指南

# 1. 故障背景与现象

  • 用户反馈: 手机/车机突然重启，或者界面完全卡死不动。
  • 技术现象: SystemServer (Android 系统核心进程) 发生 Watchdog ANR，导致 Zygote 退出，进而引发系统软重启 (Runtime Restart)。
  • 本例关键进程:
    • system_server (PID 9204): 肇事者也是受害者。
    • com.android.car (PID 10609): 触发连锁反应的源头。

# 2. 拿到 Bugreport 该怎么做？(操作SOP)

# 第一步：全局概览，找“死亡时间点”

解压 bugreport.zip，打开最大的 .txt 日志文件。直接搜索高危关键字：

  • Watchdog
  • Process .* has died
  • Fatal signal

本例日志实录: 我们在 19:59:55 附近发现了最早的异常：

// 1. 最早的源头：底层硬件服务挂了
12-24 19:59:55.486 E CAR.SERVICE: ***Vehicle HAL died. Car service will restart***

// 2. 紧接着：上层服务 CarService 自杀重启
12-24 19:59:56.818 I ActivityManager: Process com.android.car (pid 10609) has died: pers PER

# 第二步：区分“被波及应用”与“故障核心”

在 CarService 死后几秒，普通应用开始报错：

// 3. 普通应用开始 ANR (被波及应用)
12-24 20:00:02.320 E ActivityManager: ANR in com.xiaomi.smarthome_car

注意: 此时不要去分析小米智能家居为什么卡，它大概率是无辜的。当看到 SystemServer 相关的报错时，优先排查系统服务。

# 第三步：寻找 SystemServer 的“尸检报告” (关键)

SystemServer 的 ANR 详情不会全打在 logcat 里，系统会生成专门的 Traces 文件。

  • 位置: FS/data/anr/ 目录。
  • 文件名: 通常包含时间戳，本例为 anr_2025-12-24-19-59-58-255。
  • 确认方法: 打开文件，看头部 PID 是否对应 system_server (PID 9204)。

# 3. Traces 文件深度解读 (如何定性)

打开 Traces 文件，按照以下逻辑推导：

# 3.1 看主线程 (Main Thread)

主线程负责 UI 和核心消息处理，如果它卡了，Watchdog 就会杀进程。

  - waiting to lock &lt;0x00754259> (a com.android.server.am.ActivityManagerService) held by thread 23

  • 状态: Blocked (阻塞)。
  • 卡点: 正在等待一把锁 <0x00754259>。
  • 线索: 这把锁被 Thread 23 拿着。

# 3.2 分析持锁线程 (Thread 23)

  • 状态: Runnable (运行中)。
    • 关键判断: 如果它是 Blocked 或 Waiting，那是死锁。如果它是 Runnable，说明是高负载/慢操作。
  • 行为: 正在执行 getPackage (查包) 和 binarySearch (二分查找)。
  • 推论: 它不是故意不放锁，而是活儿太多干不完！

# 3.3 结合 CPU 验证猜想

回到 logcat，查看 ANR 发生时的 CPU 统计 (通常在 ANR in ... 日志附近)。

12-24 20:00:02.320 E ActivityManager: 100% TOTAL: 49% user + 43% kernel
12-24 20:00:02.320 E ActivityManager: 90% 9204/system_server: 54% user + 35% kernel
1
2
  • 数据说话: SystemServer 独自占用了 90% 的 CPU。
  • 结论: 这是一个典型的 CPU 饥饿 (Starvation) 型 ANR。AMS 线程 (Thread 23) 因为处理海量任务吃光了 CPU，导致一直占着锁，主线程因此饿死。

# 4. 完整的故障逻辑链 (总结)

  1. 起因 (19:59:55): Vehicle HAL died。底层车辆服务异常退出。
  2. 触发 (19:59:56): com.android.car (CarService) 为了自救，选择自杀重启。
  3. 风暴 (19:59:57~): CarService 的死亡导致系统状态剧变，AMS (ActivityManagerService) 需要处理大量的进程清理、权限重置和广播发送。
  4. 瓶颈 (20:00:00~): AMS 的工作线程 (Thread 23) 瞬间涌入大量查包任务，CPU 飙升，长期持有 AMS 全局锁。
  5. 崩溃 (20:00:06): SystemServer 的主线程需要发通知，但拿不到 AMS 锁，卡死超过 60秒 (Watchdog 阈值的一半或全部)，最终触发 ANR。
  6. 结局: 系统 Watchdog 杀死 SystemServer，设备软重启。

# 5. 学习心得 (排查口诀)

  • 应用 ANR 先看天：如果多个应用同时 ANR，先看 SystemServer 挂没挂。
  • SystemServer 看 Traces：logcat 里没详情，必须找 traces 文件。
  • 主线程 Blocked 找锁王：看 held by thread X。
  • 锁王 Runnable 看负载：Runnable = 忙死，Blocked = 死锁。
  • 忙死还得找源头：往前翻日志，一定有大事发生 (如 Service died)。

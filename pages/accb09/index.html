displaying性能实战

背景介绍

  • 此篇教战手册旨在帮助客户了解如何从display的角度分析性能类问题
  • 此篇教战手册的编写和举例都是基于Android S

Overview

● 卡顿问题是**系统性的复杂问题**，其成因及影响此类问题的因素众多

● **显示系统**作为手机系统中的重要组成部分，系统是否流畅通常都是通过显示投射到人眼产生的感知

● 所以**显示系统**成为卡顿问题经常涉及的模块，常常也需要作为问题切入点或问题方向判断的**主力模块**

适用对象

● 使用者必须**能熟练使用systrace**这类性能分析工具

● 使用者**对Android系统**的运行的主要组件需要**有基本了解

● 使用者**对Android显示系统**的运行，及其涉及**组件要有基本了解**

# Display Trace Common Tag

两大组成部分: 绘制（DrawFrame） + 合成 (SurfaceFlinger + HWC)

  • 绘制（DrawFrame): Surface中的空GraphicBuffer -> CPU或GPU通过Canvas -> 将数据Draw到Surface

  • 合成 (Compose): 几块有数据的Buffer -> 叠合成一张Buffer-> 送到panel显示

​ BufferQueue： 在Android系统中每一张显示图片，都是GraphicBuffer，通过BufferQueue在不同进程间流动

​ VSYNC: 控制系统绘制与合成的节律

# VSYNC信号

● 控制Display按什么样的间隔出帧，也就是帧率的基准，VSYNC Tag中颜色发生转换的分界竖线，就代表一次VSYNC信号

● VSYNC-app/sf这两个Tag是软件信号，是在HW VSYNC信号基础上重新计算以后发出的Event

● VSYNC-app 是控制绘制过程帧率的，VSYNC-sf 是控制合成过程的帧率的

● VSYNC-app/sf 通常这两者之间不会同时开始，会有一些offset先后开始

# 绘制

● DrawFrame过程： 从BQ dequeueBuffer > Draw绘制 > queueBuffer到BQ

● dequeueBuffer最后 ->Trace HWC release fence: 表示已经dequeue到了一块Buffer，但这块Buffer还在被底HWC合成使用中，

● queueBuffer最后->Trace GPU completion: 表示Buffer已经queue还给了BQ，但没有GPU还没有画完，

● HWC release: waiting for HWC release表示上一次拿这个Buffer显示的帧还在使用，需等待

● GPU completion: waiting for GPU completion出现表示GPU还没有绘制完成，需等待

从中可以看出，要么是HWC 还没有准备好；要么是GPU 还没有准备好

# 合成

● SurfaceFlinger在有的trace里也显示为UI Thread

● SF主进程结束点附近有Tag数字对应到waiting for presentFence

● presentFence: 其结束点代表SF送下来的这一帧被显示到了屏幕上，并signal前一帧的Fence

● OverlayEngine: HWC的主要进程，Trigger display driver做显示相关的动作

# buff流程过程

要理解整个绘制流程，buff的流转就需要弄清楚： 首先从绘制部分来看：vsync信号来到，通知应用主线程开始操作。主线程负责处理用户交互以及与界面相关的操作，例如布局、绘制、事件处理等。在主线程中，应用程序更新界面元素，并且响应用户的输入。在主线程准备ok好，就会将绘制命令发送给渲染线程（渲染线程会和sf线程进行交互，buff主要在这里流转）。渲染线程接受到了命令后，开始dequeue从buffQueue队列里取一个空的buff，并且经过一系列的渲染，也就是drawing绘制，将渲染好的buff通过queue放回buffQueue队列中，并且与此同时，通过acquireNextBuffer告诉surf可以从队列里取出buff进行合成了

如上图，通过acquireNextBuffer告诉surf后，surf就开始了合成的操作。sf经过合成完之后，会将buff重新放回queue中，

1. input 耗时：在处理应用的事件分发时，避免在主线程执行耗时操作；
2. animation 耗时：参与动画的元素或修改的属性太多，造成动画耗时，如果多个元素做相同的动画时，考虑使用其父元素进行动画；
3. onMeasure 耗时：APP层级太深，建议使用 LinearLayout 或 CoordinatorLayout 优化布局，减少计算的次数；
4. onLayout 耗时：如果 Activity 内容太多，可以考虑使用分页或延迟加载的方式，减少首次 Layout的布局数量；如果是在动画过程中出现多次 Layout，需要检查是否重复调用了 requestLayout；
5. onDraw 耗时：检查绘制的内容是否是必须的，如果是屏幕之外的内容，可以通过添加各类条件判断过滤掉此次绘制；此外，避免出现过度绘制的情况；
6. RenderThread 耗时：RenderThread 无法被应用直接控制，出现耗时的情况一般都是 CPU 调度出现问题，出现大范围的 Runnable 情况；或者 GPU 性能瓶颈，在 dequeueBuffer 或queueBu

# VSYNC & Fence Tag

  • VSYNC: 表示的是什么时间开始做事（绘制/合成）
  • Fence: 表示什么时间事情做完了

  • SF

HW_VSYNC_0 : SF从HWC收到的硬件VSync信号，不是一直会有，仅在必要时开启校准软件VSYNC信号

HW_VSYNC_ON_0 : 硬件VSYNC的开关，颜色翻转一次即为开启一次

VSYNC-app : SW_VSYNC信号 App渲染的VSYNC信号，基于HW_VSYNC，计算后由EventThread发出的Event

VSYNC-sf : SW_VSYNC信号 SF合成的VSYNC信号，基于HW_VSYNC，计算后由EventThread发出的Event

presentFence : MTK在S版添加的Tag，表示presentFence被Signal，其结束点与present_fence_rel:P的Tag对齐

  • HWC

VSyncThread_0 : HWC从driver收取HW_VSYNC信号的Thread，与SF的HW_VSYNC_0对应

  • Driver

DISP-HW_Vsync : Driver里的硬VSYNC是一个中断，软件以vblank的名义往HWC上报，每发送一次vblank时会打印

DISP:layer_fence_rel-P-x : layer_fence，也就是每个layer的releaseFence，如上层有HWC release的Tag，应与之对应

DISP:present_fence_rel:P : presentfence release的位置，表示新的一帧要被显示出来，旧的一帧已显示完毕，可以释放不再被使用

# HW_VSYNC异常

HW_VSYNC是VSYNC-app和VSYNC-sf的基准，如果它出现了异常，则SW的VSYNC一定会出现不正常，常见异常主要有：

  1. Resync
  2. HW_VSYNC与VSYNC-app/sf不一致
  1. Resync

  ●  前面有提到 HW_VSYNC 是不需要一直被开启的，只有SW_VSYNC偏差较大时才会开启HW_VSYNC进行校准，

  ●  所以HW_VSYNC正常应该只会出现一小段时间，如果Trace中一直出现且一直不消失，就是发生了Resync

  ●  出现Resync通常意味着有SW_VSYNC机制算出来的时间和HW_VSYNC时间偏差一直超过限制

  ●  出现这个现象通常都不是运行跑偏的问题，一般是有固定的偏差一直存在，所以这种问题一定和某些设定鱼有关，包括

      a) 上下层帧率档位不匹配，

      b)  presentFence在driver中Signal的位置有问题等

# SurfaceFlinger

Surfaceflinger的主进程，如前面提到，

  • 通常是对齐 VSYNC-sf 开始，
  • 正常情况是需要在下一个 VSYNC-sf 到来前完执行完毕的

Surfaceflinger执行时间异常主要有两种情况：

1，挤压

2，丢帧

# Surfaceflinger Tag

  • 挤压（sf进程执行时间长）

挤压通常是因为Surfaceflinger自身执行时间过长，挤压了后面一帧SF开始执行的时间，让它无法及时响应VSYNC-sf

  ● 发生挤压的情况，SF看上去就不完全follow VSYNC-sf了，但实际上并非如此，

  ● Surfaceflinger是MessageQueue驱动机制，每来一个VSYNC-sf，都表示有合成的任务要做，

  ● 发生挤压时，无法立刻对齐每一个VSYNC-sf立即响应，但Message不会丢，只是Pending状态，只要前一帧执行完立刻就会执行下一次

  ● 所以每一个onMessage处理依然可以追溯到1个准确的VSYNC-sf，这也是本次sf合成的起点，计算sf-duration，sf-worktime参考的起点依然是从这次VSYNC-sf开始

连续挤压导致丢帧

  ● 连续的挤压必定会导致后面被挤的帧被越挤越靠近后一个VSYNC-sf的时间

  ● 直到某一帧被挤到了越过了后一个VSYNC-sf的时间，那么事实上中间就有一次VSYNC-sf并没有处理Message，也就是掉了一帧，下图中蓝色圈出的 VSYNC-sf 就是被挤丢掉的帧
  
  ● 它也可以从presentFence的Tag看出，按照sf-duration的时间，从presentFence结束点回推，就可以反推出哪一个VSYNC-sf被挤丢了

GPU合成是合成的两种主要类型之一（CLIENT/DEVICE）

  ●  GPU合成的发起是在Surfaceflinger主线程中

  ●  主要特征就是会出现drawLayers的Tag

  ●  GPU合成会将指定为CLIENT合成的几层Layer由GPU合成1层，属于一次特殊的渲染，FramebufferSurface作为它的画布，RenderEngine作为它的渲染引擎

  ●  GPU合成会有它独立的BufferQueue系统，用于dequeue和queue FramebufferSurface

  ●  在S版本上使用SkiaGLThreaded引擎，GPU合成被拿到独立的线程中去完成

# GPU Compostion & HWC release Tag

要点概述：

这两个Tag是Monitor LayerFence（acquireFence/releaseFence）状态的

1，前面介绍过，这两个Tag通常和BufferQueue一起出现，对于理解BufferQueue的行为和分析问题，正确理解这两个Tag非常重要：

GPU completion: 字面上理解就是等GPU绘制完成，Signal AcquireFence

HWC release: 字面上理解就是等HWC合成使用完毕，Signal ReleaseFence

2，由代码可知这两个Tag填入的出处在GUI Surface的dequeueBuffer和queueBuffer:

3，而真正打印这个Trace是在FenceMonitor的Thread中：

 ●  由此可以知道这两个Tag并不是代表真正的Fence，而是一个monitor Fence，track Fence状态的Tag

  ●  它monitor的是某一个Surface所用Buffer的Fence，也就是LayerFence的状态

  ●  如果在这个monitor thread开始之前LayerFence已经被Signal了，则这两个Tag就不会出现

       a) dequeueBuffer或queueBuffer最后出现（fence %u has signaled），GPU completion & HWC release里就不会出现waiting

       b) dequeueBuffer或queueBuffer最后出现（Trace %s fence %u）,  GPU completion & HWC release里就会出现waiting

  ●  waiting for GPU completion和waiting for HWC release后面的数字是Fence计数的idx， 但互相之间相同的数字并没有直接固定的对应关系，

dequeueBuffer变长的直接影响因素：

  • 如上图，dequeueBuffer是从BufferQueue里去取Buffer，所以dequeue变长的最直接原因是Buffer都被拿走了还未还，拿不到Buffer

  Alloc慢  ------ alloc慢是系统在一定Loading情况下比较常见的一种情况，BufferQueue里只有dequeueBuffer的时候会去检查是否需要Alloc Buffer

   什么情况下会去alloc Buffer?
      
     a) BufferQueue刚刚Create，首次使用Buffer的时候，会需要Alloc
     
     b) 当Buffer的Size/Format或一些Usage属性突然发生改变的时候，需要重新Alloc Buffer

     c) 在Composer进程中出现Alloc，一般是HWC需要用到MDP，MDP一般会使用3块Buffer，所以此时起始的3帧第一次dequeueBuffer的时候会Alloc Buffer


  alloc慢一般都是需要去查看系统的内存使用状况，正常情况下都是很快的，除非系统内存紧张，需要先回收内存，或干脆就是分配不出的情况下会Alloc很久或失败

出现这种情况应该如何处理：

  a. 仔细查看dequeueBuffer变长之前的几帧，看是否有某一帧特别慢，

     ● 有某一帧特别慢，则直接追究这一帧变慢的原因
              

  b. 如果没有哪一帧特别慢，都很平均地慢，

     1）仔细check一下draw和compose的每个阶段，看有没有哪个阶段明显比较慢

     2）对比正常不慢的情况，分析慢的原因，对比CPU Loading，图层数目等看是否有明显差异

     3）通过一些Common的性能调节手段（拉CPU/GPU/DRAM等）看能否改善


  c.  如果是两个都不慢，那就要去看Producer和Consumer的速度是否匹配

     1）Producer和Consumer必须以接近的速度进行生产和消费，差异太多就会造成BufferQueue迅速被消耗完，破坏正常地轮转

     2）在默认设计上通过VSYNC-app & VSYNC-sf，以及合理的Buffer数量，S版上还要正确设定app-duration & sf duration来维持平衡

     3）除了以上设定问题，通常是有app故意设计DrawFrame不听VSYNC-app才会和VSYNC-sf出现不匹配

     4）其次还有一部分可能是BufferCount数量设置不合理，

        ● 对于不听VSYNC-app的情况，BufferCount太多它也可能会在BufferQueue开始阶段绘制太多帧，造成任务堆积无法被及时处理

        ● BufferCount太少也不行，会因为不能及时拿到可用Buffer而造成BufferQueue轮转阻塞

          （S版上default BufferCount是根据帧率和Duration计算出来的） 此种情况可以视情况来调整BufferCount看能否得到改善

 ● queueBuffer同样也是不需要check Fence状态的，所以Fence并不会直接导致queueBuffer变长 

  ● queueBuffer变长的原因比较直接，用下图就可以解释的很明确

  ● 下图中97072  dequeue trig了HWC  release 3155，对应的queue trig了GPU completion 3156，GPU受到了HWC release的影响

总结

 queueBuffer变长的直接原因通常是它前面一次的queueBuffer还没有完成，它queue出去的Buffer GPU仍然在绘制中，

 此时queueBuffer会出现waitForever，后面一次的queueBuffer必须等它完成之后才能queue出去

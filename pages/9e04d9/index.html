sf绑大核

# 背景

G99/G96 项目使用DDR4 双通道器件，高刷（120hz）的机器上，空载sf肥帧，负载的时候sf合成超时。

超时原因是sf跑在小核上，小核满频后还是频率不够，所以需要sf绑到大核上。

# 前置知识

# 系统编译——Android.mk / Android.bp 条件编译

参考文章：https://blog.csdn.net/tahlia_/article/details/105494446

目的：多个平台引用同一个模块，但其中一个模块需要对其修改。因此，基于自定义编译，不同平台可快速进行优化方案和非优化方案的切换，便于在不同阶段的各个平台能不受影响快速切换方案

到了，Android 9.0+ —— Android.bp实现条件编译，其编译方式已改变，google将条件编译进行分家，Android.bp负责纯粹配置，引入Go文件负责进行流程结构判断。架构如下所示：

查看其原本的组为system-background组，并且只能跑在0-3核上

后面修改render绘制线程的cgroup组，将其改到foreground组，对应的是0-7，原本的cgroup组只能跑在0-3

方案缺点：

  1. RE线程参与工作的时候是sf上有gles合成的时候。所以当sf没有gles合成的时候是不生效的。
  2. sf有gles合成的时候，如果大部分耗时都是sf running时间长，re耗时很短的时候，瓶颈还是在sf线程上。因为其只是绑到了0-7组，优先级较低的话，还是抢不到cpu资源

# SF邦大核二-——kernel层进行绑核

通过kernel层设置进程优先级，并且绑定cpu，这里不多研究了，主要看方案三吧

方案缺点

经常出现HANG问题

  1. 代码里针对6+2的结构写死的，不是动态适配的。
  2. 如果高负载的时候，会导致大核上其他进程抢占不到

# SF邦大核方案三-应用层调整cgroup

基于以上sf邦大核一和二的缺点，诞生了sf邦大核方案三

该方案考虑到6+2的结构所以只把launcher uithread,launcher renderthread, sf main thread放在aniboost下。

其中launcher uithread,launcher renderthread根据是否绑核，根据场景自行调用

# 原理

使用CGroup的子系统cpuset 限制可运行的cpu。

  1. 参考cpuset下其他目录的创建方式，创建/dev/cpuset/anibooster 目录

  2. 将sf开机后绑定到anibooster的group中

  3. anibooster下的cpus 默认是小核

  4. 关键sf耗时场景把anibooster下的cpus写成大核

  5. 场景结束后，cpus改成小核

  6. 创建anibooster目录

patch解读：

在开机后系统解析init.rc 中创建目录。copy目录，修改ueser和分组。修改权限。后续要往cpus节点写数据，所以改cpus的权限

/system/core/rootdir/init.rc

    #SPD: add boost_cpu for big core by fan.feng1 20221021 start
    mkdir /dev/cpuset/anibooster
    copy /dev/cpuset/cpus /dev/cpuset/anibooster/cpus
    copy /dev/cpuset/mems /dev/cpuset/anibooster/mems

    chown system system /dev/cpuset/anibooster
    chown system system /dev/cpuset/anibooster/tasks
    chown system system /dev/cpuset/anibooster/cpus
    chmod 0664 /dev/cpuset/anibooster/tasks
    chmod 0664 /dev/cpuset/anibooster/cpus
    #SPD: add boost_cpu for big core by fan.feng1 20221021 start

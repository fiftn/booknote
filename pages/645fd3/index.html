# 中高端项目应用冷启动慢

# 问题描述

抓取冷启动的systrace，发现应用在启动过程中，主线程会有很多跑小核的情况，应用主线程跑小核，running时间较长，影响应用冷启动时间

# 优化思路

要优化应用冷启动的速度， 主要是提升应用跑大核的概率，应用的优先级为110，容易跑大核，但是也会经常被分配到小核，这个时候可以使用MTK的task_turbo来优化，**这块具体主要是学习这个方案，可以看mtk方案板块学习下这个taks_turbo**

# 优化结果

应用优先级被设置为100，启动的时候必然会跑在大核上，提高了应用的冷启动时长

# 低端项目冷启动慢

# 问题描述

中高端项目，可以通过优化调度的方式提升应用冷启动的速度，但是在只有4核的项目中，上述的方案就失效了，如上，冷启动应用有较长的白屏，影响体验

查看systrace，主要是running时间长和sleepiong时间长，但是此时cpu已经跑满了，也就是说此时性能已经到达了瓶颈，此时无法通过提高性能来优化，只能去优化降低消耗的资源

# 优化思路

针对低端的机器，优化调用和提升优先级的方案，都无法有效提升应用冷启动的速度。这时候就需要挖掘用户对这个场景的真实感受，通过沟通，用户主要的诉求就是白屏的时间长，如果能解决白屏的问题，也能改善用户体验

对此，对这个场景进行研究后，可以利用原生的SplashScreen机制，配合截图，在应用冷启动时，先显示一张首帧的截图，等界面加载完成后，在隐藏截图无缝衔接，让用户在冷启动应用时有热气的的感受。

具体的方案，我就不写了，可以跟随思路，掌握挖掘用户的核心思想

# sf绘制线程mdp超时

# 问题描述

现象：demomode apk在滑动时候卡顿，该apk图层中带有视频

前面的绘制都是ok的，到此时突然就卡顿，

从buff堆积来看：

关于显示流程，具体可以mtk显示专栏，以及systrace学习专栏；这里buff明显在堆积，原理就是sf合成存在耗时操作，导致其回调信息vsync-sf慢了，下一个sf也就无法及时合成，也就是消费端无法快速处理这些buff，导致buff堆积起来

从vsync信号来分析，可以看到app信号正常，但是sf信号后面一帧突然回调就变长了：

可以看到这一桢vsync-sf信号变长，是因为这一桢的sf无法回调，present正在等待，往下追的话，其在等待renderEngine，但是其也在等待，往下追，其在等待mdp的合成，由此看来主要就是mdp耗时的问题

当图层太复杂的时候，sf就会一直往下请求mdp合成

结论：需要显示的图层太复杂，gpu无法绘制，需要mdp介入，耗时太长

# 优化思路

询问了mtk后，这块mdp是mtk负责， 我们公司并没有相应的owner：

设置这个属性即可：adb shell "setprop vendor.mtk.c2.vdec.force.output.cc 1" ， mtk回复：

请仿照forcecc.diff的改法，并添加app的白名单,对特定app让decoder 强制cc，跟我给你的cmd是相同的作用。
问题原因：
	video decoder 出mtk私有yuv格式，hwc推给GPU合成的时候，GPU不吃mtk私有yuv格式，就呼MDP转成公有yuv格式，在高刷场景下。MDP处理不过来。
解决方法：
	让decoder 强制cc，出成公有yuv格式。让这个格式转换跟随视频的帧率来处理，而不是跟随屏幕刷新率。通常屏幕刷新率比视频帧率高很多。

# 近期任务界面点击卡片进入界面应用动画抖动

# 问题描述

在这个场景中，由于圆角动画的存在，会使用GPU来合成，GPU合成本身就会比较耗时

sf在一帧的时间内不能完成合成任务，会出现丢帧的情况

此外launcher在这个过程中，动画的卡顿现象会随着卡片数量的增加而变得更卡，抓取systrace发现动画的耗时太长，这也是造成动画抖动的重要原因

# 优化思路

sf耗时长的问题，在解说抖动问题中引入的调度优化方案，也覆盖了该场景，但是依然会存在验证的抖动问题，究其原因主要还是应用自身的逻辑耗时太长，无法满足动画的需要。虽然找到了原因，动画耗时太长，但是从systrace中是无法看到底层的，这时候就需要看具体的代码逻辑，这里使用traceView对具体的逻辑进行简单的分析：

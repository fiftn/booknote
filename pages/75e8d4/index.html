ANR

这一板块主要介绍ANR机制

# ANR是什么

ANR(Application Not responding)，是指应用程序未响应，Android系统对于一些事件需要在一定的时间范围内完成，如果超过预定时间能未能得到有效响应或者响应时间过长，都会造成ANR。

# ANR发生的场景

触发ANR的条件则是主线程阻塞超时

场景 超时时间
Service ANR 前台20s，后台200s；startForeground超时10s
Broadcast ANR 在执行前台广播的onReceive()函数时10s没有处理完成，后台60s
Input ANR 按键或触摸事件在5s内无响应
ContentProvider ANR 内容提供者超时，10s，少见

# 常见的原因

  • 主线程binder耗时
  • 主线程i/o耗时
  • 死锁
  • 主线程等锁耗时
  • activity resume慢/焦点窗口切换慢（针对Input anr）
  • 主线程有太多消息要执行，导致对应组件消息执行delay。
  • 主线程前面的消息执行耗时，导致后面的消息delay。
  • 跟手机当时状态有关，内存/cpu等
  • startForeground未在Service的onStartCommand中执行

# 总结来说，发生ANR有以下三种原因：

  • 在主线程进行了一些耗时操作
    • 比如主线程阻塞、挂起、死锁、死循环、耗时操作等
    • 一般解决办法：开辟单独的子线程来处理耗时阻塞事务
  • cpu满负荷、I/O阻塞
    • 比如cpu被其他进程抢占完，调度不及时，和io读写等待
    • 一般解决办法：cpu这种需要具体分析，io阻塞也可以开子线程的方式异步执行
  • 内存不够用
    • 比如内存紧张、没有资源分配，以及内存泄漏等等
    • 一般解决办法：增大VM内存，排查内存泄漏

  • 线程名：main
  • prio：线程优先级
  • tid：线程内部id
  • 线程状态：Runnable，线程在虚拟机中的状态有native、blocked、suspended、timewaiting、runnable等

  • self：当前的线程地址
  • sysTid：线程真正意义上的tid
  • nice：调度优先级
  • cgrp：进程所属的进程调度组
  • sched：调度策略
  • handle：函数处理地址
  • state：进程状态
  • schedstat：cpu调度时间统计
  • utm/stm：用户态/内核态的cpu时间
  • core：该线程最后运行的所在核
  • HZ：时钟频率

nice值越小则优先级越高，此处的nice=0，优先级还是比较高的

schedstat括号中的三个数字分别是running、runnable、switch，紧接着的是utm和stm

  • running：cpu运行的时间，单位ns
  • runnable：rq队列的等待时间
  • switch：cpu调度切换次数

# 预防措施

  • 使用AsyncTask处理耗时IO操作。
  • 使用Thread或者HandlerThread时，调用Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)设置优先级，否则仍然会降低程序响应，因为默认Thread的优先级和主线程相同。
  • 使用Handler处理工作线程结果，而不是使用Thread.wait()或者Thread.sleep()来阻塞主线程。
  • Activity的onCreate和onResume回调中尽量避免耗时的代码。 BroadcastReceiver中onReceive代码也要尽量减少耗时，建议使用IntentService处理。

将所有耗时操作，比如访问网络，Socket通信，查询大量SQL 语句，复杂逻辑计算等都放在子线程中去，然后通过handler.sendMessage、runonUIThread、AsyncTask、RxJava等方式更新UI。无论如何都要确保用户界面的流畅度。如果耗时操作需要让用户等待，那么可以在界面上显示度条。

# 关键词信息

# kswapd

这个是linux中用于内存回收的内核线程，如果在system日志中发现该线程在cpu中占用过高，则说明当前的系统内存紧张，或者内存碎片化严重，需要进行file cache回写或swap交换

# mmcqd

内核线程，主要作用是把上层的io请求进行统一管理和转发到driver层，当该线程的cpu占用过高，说明系统存在大量的文件读写。一般kswapd和mmcqd经常是同步出现的

# binder_sample

监控每个进程主线程的binder transaction情况，超时会打印日志

# ”show xxx“提示

android系统在一些频率调用的接口中，分别在方法前后利用checktime检测，以判断本次函数执行耗时是否超过设定阈值，当有类似的打印时也可以辅助参考

# lowmemkiller

kernel日志中有时候会打印这个，主要是内存低被lmk给kill掉

# 更多的关键词

system.err,system.out,dvm_lock_sample(某线程等待超时),binder thread(线程池用完),am_meminfo等

# 一切都正常时？

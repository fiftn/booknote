# systrace基础信息

# 定义

Systrace 允许您在系统级别（如SurfaceFlinger、WindowManagerService等Framework部分关键模块、服务、View系统等）收集和检查设备上运行的所有进程的计时信息。 它将来自Android内核的数据（例如CPU调度程序，磁盘活动和应用程序线程）组合起来，以生成HTML报告。

# 抓取方法

使用bat脚本抓取，脚本如下；抓取完成后使用mtk工具，或者python解压出来

set filename=%date:~0,4%%date:~5,2%%date:~8,2%%time:~0,2%%time:~3,2%%time:~6,2%
set "filename=%filename: =0%"
adb  shell atrace -t 5 -b 102400 gfx input sched disk view webview wm am sm video hal res dalvik bionic power pm ss sched freq idle memreclaim binder_driver binder_lock camera aidl irq > C:\Users\tingjiang.wang\Desktop\%filename%

# systrace基础教程

# 线程状态

使用Google Chrome(其他浏览器很可能打不开)将这个文件打开进行分析，界面如下： 在进程的上面有一条很细的进度条，包含了该线程的状态：

绿色： 正在运行（调度程序认为它正在运行）。

这个状态是正常的状态，但是遇到了一般倾向于看：

  • 是否频率不够？
  • 是否跑在了小核上？
  • 是否频繁在 Running 和 Runnable 之间切换？为什么？
  • 是否频繁在 Running 和 Sleep 之间切换？为什么？
  • 是否跑在了不该跑的核上面？比如不重要的线程占用了超大核

灰色： sleeping，无任务需要执行。但也有可能因为互斥锁被阻塞

蓝色： 可以运行（它可以运行，但还未被调度运行）。

整体runnable持续的时间越长的话，也就表示cpu的调度越繁忙

  • 是否后台有太多的任务在跑？
  • 没有及时处理是因为频率太低？
  • 没有及时处理是因为被限制到某个 cpuset 里面，但是 cpu 很满？
  • 此时 Running 的任务是什么？为什么？

红色： 不间断的睡眠（通常发生在内核锁上），

一般是陷入了内核态，有些情况下是正常的，有些情况下是不正常的，需要按照具体的情况去分析

橙色： 由于I / O负载导致的不间断睡眠，表示线程在等待io

但是如果出现大量的io不可中断，并且点进去看见其参数是wait_on_page_locked_killable，则表示系统进入了低内存的状态 申请内存的时候触发 pageFault, linux 系统的 page cache 链表中有时会出现一些还没准备好的 page(即还没把磁盘中的内容完全地读出来) , 而正好此时用户在访问这个 page 时就会出现 wait_on_page_locked_killable 阻塞了

# kernel

kernel里面主要显示就是cpu信息：

  • cpu频率变化、限频情况
  • 任务执行情况
  • 大小核调度情况
  • cpu boost调度情况

点击时间片，可以查看详细信息：

其中，最后的stateWhenDescheduled表明了被调度前进程最后的状态

linux进程状态可分为六种：

  • R 运行状态（running）
  • S 睡眠状态（sleeping）
  • D 磁盘休眠状态（Disk sleep）
  • T 停止状态（stopped）
  • Z 僵尸状态（Zombies）
  • X 死亡状态

其中可能还会在状态上带上特殊标志：

  • < 表示进程优先级比较高
  • N 表示进程优先级比较低
  • L 表示进程有页面文件锁定在进程中
  • s 表示进程为控制进程，如systemd进程
  • I 表示进程是多线程
  • + 表示当前的进程运行在前台（后台运行在命令之后加 &）

# systemserver

systrace中跟系统相关的，基本都在systemserver中，主要包括：

  1. input事件

input包含了触摸事件（down，up，move）以及key事件(home key，back key)，事件大致流程：

  • 触摸屏根据采集率每隔几毫米扫描一次，如果有触摸事件，则上报到对应驱动
  • inputReader读取触摸事件交给inputDispatcher进行事件分发
  • inputdispatcher将触摸事件发给了注册了input事件的app
  • app拿到事件之后，进行input事件分发，如果此事件分发过程中，app的ui发生了变化，那么会请求vsync，则进行一帧绘制

input事件在性能优化中一般用来查看报点情况，从而分析滑动过程中动画抖动问题或查看一些异常情况

  1. binder

systemserver由于大量的基础服务，所以进程间的通信非常繁忙，且大部分通信都是通过binder，因此binder在其中的作用十分关键。很多时候当后台有大量的app存在的时候，systemserver就会由于binder通信和锁竞争，导致系统或者app卡顿。

  1. 窗口动画

systemserver中涉及到窗口动画的有两个进程，分别是android.anim 和android.anim.if ，在systrace中名称为animating 和animator

  1. backgroundThread线程，在系统中使用比较多，但是对性能没有要求的任务，一般都会放到该线程中执行
private BackgroundThread() {
    super("android.bg",android.os.Process.THREAD_PRIORITY_BACKGROUND);
}

# vsync

Vsync 信号可以由硬件产生，也可以用软件模拟，不过现在基本上都是硬件产生，负责产生硬件 Vsync 的是 HWC,HWC 可生成 VSYNC 事件并通过回调将事件发送到 SurfaceFlinge , DispSync 将 Vsync 生成由 Choreographer 和 SurfaceFlinger 使用的 VSYNC_APP 和 VSYNC_SF 信号

在trace中的具体表现：

vsync的时间间隔由硬件决定，如果在60hz上，一帧为16.6ms，以此类推；为了配合vsync更好工作，又引入了两个新概念：triple buffer和choreographer

# Triple Buffer

简单来说就是增加了第三个缓冲buff，使得图像更不容易卡顿

# choreographer

作为一个代理角色，提供上层app的消息处理时机，更多信息可以参考https://androidperformance.com/2019/10/22/Android-Choreographer/#/%E5%BC%95%E5%85%A5-Choreographer

# su'faceflinger

终端合成功能，接收多个来源，并对他们进行合成，然后送到显示设备https://www.androidperformance.com/2020/02/14/Android-Systrace-SurfaceFlinger/

# binder

很多时候的卡顿问题都是因为跨进程的binder通信的时候，锁竞争导致binder通信事件时间变长，影响了调用端。最常见的就是应用渲染线程dequeuebuffer的时候，sf的主线程阻塞导致dequeuebuffer耗时，从而导致应用渲染出现卡顿。

在root版本中，执行adb shell am trace-ipc start，可以看到具体的binder信息

# 现象分析

抓取trace观察发现，其中sf耗时较长：

抖动的关键点在于应用的renderThread耗时较长，无法在一个绘制周期内准备好一帧的数据

因此，bufferqueue里面也没有对应的buffer

# 优化思路

整个动画过程是sf和绘制线程耗时较长，无法满足动画需要，并且这两个线程运行在cpu小核上，那么可以将其绑定到大核上尝试：

这里的领悟就是，一个系统的好坏最好的就是其能否充分的调度各种资源。这里绑定到大核，有人会疑问，那不是会占用大核的资源吗，万一这时候有重要的线程正在跑怎么办。这个时候就是一个重要性的概念了，用户看到的是第一视觉，永远都是最重要的，因此肯定需要满足用户此时不卡顿的需求。暂时绑定到大核上，然后再取消绑定

具体的做法是：framework层调用接口开始绑定动画任务 ——》接口层根据传递过来的参数，写入节点 ——》kernel层根据节点的值，对关键任务进行绑核

这也其实就是sf和绘制线程绑中大核的方案了，这块想要了解的更清楚，可以具体看我研究tracnssion方案版本中的sf绑核方案

解决了关键任务的大核后，抓取trace验证，发现此时sf跑在大核上，但是queueBuffer此时变成了阻塞sf的关键

大胆猜测：此时虽然sf和绘制线程都在大核上，但是当系统资源紧张的时候，绘制线程依旧会耗时，这个时候sf使用的也就只能是之前堆积的buff，但是mtk中的设定是buff最高上限只会给到3，这个时候，将其修改成6，就会有改善。

上述的优化完成后，在mt6768平台上，负载依旧会出现抖动的问题，平台无法完全解决动画抖动的问题，此时就需要从动画的角度去优化，目前的动画在launcher完成，涉及到launcher主线程，launcher的绘制线程，于是和设计师沟通：

从launcher部门得知：针对每个图标单独运动，动画的数量较大，在中低端平台无法满足性能需求；于是采用窗口动画进行改造
